## V2.0 Lite 交付边界

Windows 端使用 `moment-sync/v1`（可配置）下的 `manifest.json`、`locks/current.json` 和 `snapshots/` 对象完成快照同步。同步包覆盖事件、日常、浮动事项、长期任务、模板和全部归档月文件；仅同步 `tagColors` 与候选宽限设置。主题、时区、通知、托盘、快捷键、钩子和数据目录始终保留在本机。

AK、SK 与同步口令只保存在当前 Windows 用户的凭据管理器，`sync.json` 及远端快照均不写入这些凭据。快照使用 zstd 压缩、Argon2id 密钥派生与 AES-256-GCM 加密。

使用规则是“一名用户、同一时刻一台 Windows 设备”。客户端持有 30 分钟租约并定期续租；其他设备有未过期租约时不得接管。首次同步发现本地和远端都有数据时，必须由用户选择上传本地、下载远端或取消，绝不自动合并。断开同步只清除本机配置与凭据，不会删除本地业务数据或七牛对象。

Android 的适配将在 Windows 版本的实际使用稳定后单独规划，届时仍需补充后台生命周期、凭据安全存储、移动端界面及异常退出恢复测试。

当前 Windows 版本已验证：S3 虚拟主机下载、远端 manifest 读取、快照下载解密、启动同步、设备租约和锁释放均正常。随后补充了过期设备锁必须用户确认接管的 IPC 与设置页操作。Android 工具链和工程基础已准备完成，但 Android 同步功能仍按本计划延后。

## 1. 文档目的

本文档用于规划「此刻 MOMENT」从单设备本地应用升级为 Windows、Android 多设备协同应用的技术路线。

目标是在不增加服务器固定成本的前提下，保留当前“本地优先、数据自持、离线可用”特性，并实现 Windows、Android 设备之间的低频数据同步。

## 2. 当前现状

当前应用是一个基于 Tauri 2、React、TypeScript 和 Rust 的 Windows 桌面应用。

主要特点：

- 数据保存在本地 JSON 文件中，不依赖云端服务。
- 前端通过 Tauri IPC 调用 Rust 后端。
- `schedule-core` 负责数据模型、存储、候选推荐、重复事件、自然语言解析、搜索和统计。
- 事件、日常、浮动事项、长期任务和归档已经具有稳定 ID。
- 数据普遍包含 `createdAt`、`updatedAt`、`deletedAt` 等字段。
- 当前已经具备原子写入、备份、软删除、版本迁移和外部修改检测。

当前的主要限制不是单实例保护，而是数据只存在于当前设备。不同设备之间没有统一的数据源和同步协议。

本阶段确定采用“单设备互斥同步”模式：严格要求同一时间只有一台设备进入编辑状态，设备启动时下载七牛云快照，退出时上传新快照。未来如果需要同时使用多个设备，再升级为同步 API + 数据库的增量同步模式。

## 3. 总体目标

当前采用“本地优先客户端 + 七牛 Kodo 快照 + 设备占用锁”架构：

```text
Windows / Android
        ↓
本地 JSON 数据
        ↓
七牛 Kodo 私有空间
        ↓
另一台设备启动时下载
```

每台设备都保留本地数据。设备启动时下载远程快照，使用期间离线工作，退出时上传完整快照。应用通过远程 manifest、版本号和设备锁避免两个设备互相覆盖。

不建议把现有 JSON 数据目录直接放入 OneDrive、坚果云或其他网盘目录。文件级同步无法可靠处理并发编辑、删除和恢复。

## 5. 当前同步模型：快照同步

### 5.1 快照文件

当前数据仍以 `events.json`、`routines.json` 等文件为主要存储单位，但上传时不应逐个覆盖远程文件，而应将完整数据打包成一个一致的快照。

推荐对象结构：

```text
schedule-sync/
├── manifest.json
├── snapshots/000001.zip
├── snapshots/000002.zip
└── locks/current.json
```

快照可以是 JSON 压缩包；正式使用时应优先使用加密压缩包。

### 5.2 manifest 和版本号

```json
{
  "schemaVersion": 1,
  "revision": 123,
  "snapshotKey": "snapshots/000123.zip",
  "updatedAt": "2026-09-18T12:00:00Z",
  "updatedBy": "windows-main"
}
```

上传前必须再次读取远程 `manifest.json`。只有远程 `revision` 没有变化时，当前设备才允许发布新快照。

### 5.3 设备占用锁

```json
{
  "deviceId": "windows-main",
  "deviceName": "Windows电脑",
  "revision": 123,
  "lockToken": "随机令牌",
  "lockedAt": "2026-09-18T10:00:00Z",
  "expiresAt": "2026-09-18T10:30:00Z"
}
```

启动时：

1. 下载当前锁。
2. 没有有效锁时获取锁。
3. 锁属于其他设备时禁止编辑。
4. 锁过期时提示用户确认接管。
5. 正常退出时上传快照并释放锁。

锁是保护机制，不是绝对的分布式锁。因此退出上传前必须再次检查锁令牌和远程版本；检查失败时禁止覆盖远程数据。

### 5.4 启动、使用和退出流程

启动：

1. 检查本地是否存在未上传快照。
2. 获取或确认设备锁。
3. 下载远程 manifest 和最新快照。
4. 备份当前本地数据。
5. 解包并加载远程数据。

使用中：

- 正常写入本地 JSON。
- 重要操作后可延迟上传一次快照。
- 长期任务会话暂停或结束后建议立即上传。
- 提供“立即同步”按钮。

退出：

1. 完成当前写入。
2. 重新读取远程 manifest。
3. 校验 revision 和 lockToken。
4. 生成新快照。
5. 上传新快照。
6. 更新 manifest。
7. 释放设备锁。

如果上传失败，应保留本地未上传状态，不能清除本地数据。

### 5.5 Android 异常退出

Android 不能保证每次被系统回收时都能执行退出逻辑。因此需要：

- 切到后台时尝试同步。
- 提供手动同步按钮。
- 下次启动检测未上传状态。
- 设备锁设置过期时间。
- 接管过期锁前要求用户确认。

### 5.6 未来的增量同步模型

如果未来需要多个设备同时在线，再引入变更记录：

建议的变更记录字段：

```text
changeId
accountId
deviceId
entityType
entityId
operation
payload
revision
createdAt
```

`entityType` 可以是：

- `event`
- `routine`
- `task`
- `longTask`
- `longTaskSession`
- `archiveEntry`
- `template`
- `tag`
- `config`

### 5.7 客户端同步状态

每台设备需要维护：

```text
deviceId
lastPulledCursor
pendingMutations
syncState
lastSyncAt
```

未来增量同步的本地写入流程：

1. 用户修改数据。
2. 立即写入本地存储。
3. 生成一条待上传变更。
4. 网络可用时上传变更。
5. 服务端返回版本号。
6. 客户端拉取其他设备的变更。
7. 合并本地数据并刷新界面。

### 5.8 幂等性

未来引入同步 API 后，每条本地变更必须有稳定的 `changeId`。当前快照模式则使用 `revision`、`lockToken` 和快照对象键保证重复退出上传不会产生多个生效版本。

## 6. 当前冲突处理与未来扩展

当前方案通过“单设备互斥”规避大部分并发冲突，不允许两个设备同时编辑同一份数据。

当前必须处理的异常包括：

- 远程版本在退出前发生变化。
- 当前设备锁已被其他设备接管。
- 上传中断或七牛不可用。
- Android 被系统回收，没有执行正常退出流程。
- 本地存在未上传快照。

处理原则：发现远程版本或锁不一致时，禁止覆盖远程快照；将本地数据保留为独立备份，并提示用户选择“重新下载”或“保留本地快照”。

未来升级为同时在线的增量同步后，再采用以下细粒度冲突策略：

不同数据类型采用不同策略：

| 数据类型 | 推荐策略 |
| --- | --- |
| 事件、日常、浮动事项 | 记录级版本控制；并发修改时保留冲突信息 |
| 长期任务本体 | 版本检查，冲突时生成冲突副本 |
| 长期任务会话 | 追加合并，不覆盖其他设备记录 |
| 归档条目 | 按条目 ID 合并 |
| 标签 | 集合合并，删除使用软删除 |
| 模板 | 记录级版本控制 |
| 配置 | 拆分账户配置和设备配置 |
| 正在运行的计时器 | 不直接同步运行状态，只同步结束后的会话 |

增量同步版本可以采用“最后修改优先 + 冲突副本保留”的方式：

```text
电脑修改事件 A
手机同时修改事件 A
        ↓
保留最新版本
同时保存冲突副本
        ↓
用户选择最终版本
```

不能简单地使用最后写入覆盖，否则可能造成日程内容无提示丢失。

## 8. 账户和设备管理

当前快照方案只面向个人使用，不强制引入账户系统。设备身份由本地生成并写入同步锁，七牛空间和对象前缀由用户自行配置。

未来改为同步 API 后，需要增加：

- 用户注册和登录
- 一个账户绑定多个设备
- 设备名称和设备列表
- 设备配对或二维码绑定
- 注销当前设备
- 撤销其他设备访问权限
- 登录令牌刷新和失效

当前版本可以使用手动配置的同步 Token 和同步密码。未来引入同步 API 后，再使用账号密码、一次性设备配对码或 Passkey。

## 9. Android 端适配

Tauri 2 可以作为 Android 端基础，但当前项目中包含 Windows 专属能力，需要做平台抽象。

需要适配：

- Windows 托盘改为 Android 通知和应用入口。
- Windows 全局快捷键只在 Windows 保留。
- 数据目录选择改为 Android 应用内部存储。
- 页面布局改为响应式手机布局。
- 增加 Android 通知权限处理。
- 处理后台同步、应用挂起和应用被系统回收。
- 处理长期任务计时器在后台暂停和恢复的情况。

Android 第一阶段只要求：

- 打开应用时自动同步。
- 手动下拉刷新。
- 编辑后后台上传。
- 网络恢复后自动重试。

后台定时同步可以放到后续版本，避免第一版被 Android 后台限制拖慢。

## 10. 数据安全

### 10.1 当前快照方案

- 全程 HTTPS。
- 七牛空间设置为私有。
- 不在客户端写入七牛 SecretKey。
- 使用受限、短期或手动配置的上传 Token。
- 上传前使用同步密码加密快照。
- 每次覆盖前保留旧版本快照。
- 本地保留最近的未上传快照。
- 客户端本地数据继续保留。
- 支持完整数据导出。

### 10.2 后续增强

- 端到端加密。
- 服务端只保存加密 payload。
- 用户设备保存加密密钥。
- 恢复码和密钥备份。

端到端加密会增加服务端搜索、冲突展示和账户恢复的复杂度，因此不作为同步 MVP 的阻塞条件，但数据结构应预留加密 payload 能力。

## 11. 现有数据迁移

首次启用同步时：

1. 保留当前 Windows 本地数据。
2. 配置七牛空间、同步 Token 和同步密码。
3. 扫描现有 JSON 文件。
4. 保留原有 ID 和时间戳。
5. 生成第一个加密快照并上传。
6. 写入初始 `manifest.json` 和 `revision`。
7. Android 配置相同同步信息后下载快照。
8. 新设备完成本地初始化。

迁移过程中必须自动生成原始数据备份，不能直接覆盖用户现有文件。

归档数据在当前快照模式下随完整数据一起同步；未来升级为增量同步时，再以 `archiveEntry` 为同步单位，同时继续兼容现有月份文件导入导出。

## 13. 建议实施顺序

```text
快照与设备锁改造
        ↓
七牛配置与加密上传
        ↓
Windows 单设备同步
        ↓
Android 启动 / 手动同步
        ↓
异常退出与恢复
        ↓
（可选）同步 API 与数据库
        ↓
真正的增量同步
```

当前不需要先实现实时协作。应先把快照一致性、设备锁、异常退出和数据恢复做可靠，再考虑增量同步。

## 14. MVP 验收标准

V2.0 Lite 验收标准：

- Windows 和 Android 可以配置同一个七牛同步空间。
- 两台设备可以查看同一份事件、日常、任务和长期任务。
- 启动时可以下载最新快照。
- 退出时可以上传新快照。
- 同时打开两个设备时，后启动设备会被阻止编辑。
- 远程版本变化时不会静默覆盖。
- 上传失败时本地数据和未上传快照不会丢失。
- Android 被系统回收后，下一次启动可以恢复并提示同步。
- 长期任务会话不会因快照覆盖而重复或丢失。
- 快照可以加密、导出和恢复。
- 用户可以导出和恢复完整数据。
- 原有 JSON 数据可以平滑迁移。

## 15. 最终建议

当前推荐将项目升级为：

> 保留本地优先特性，以七牛 Kodo 保存加密快照，通过单设备占用锁、启动下载、退出上传和远程版本检查实现低成本多设备同步。

未来如果需要同时使用多个设备，再升级为“同步 API + 数据库 + 增量变更日志”的完整多端架构。当前方案能够最大限度复用现有 Rust 核心、数据模型和前端页面，同时避免直接把数据目录放入网盘导致文件级冲突。
